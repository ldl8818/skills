# push

用户调用此命令（如 `push`、`/push`、`执行push`、`执行 push` 或 `执行 push@push`）即授权主 Agent 按下述范围规则直接提交并推送。所有风险档位均由主 Agent 执行，不为 push 启动子 Agent 或嵌套模型 CLI。仅讨论或要求修改本命令不视为执行授权。附加范围：$ARGUMENTS

## 主 Agent 准备

1. 复用当前对话、已读且未变的规则、进度和验证证据；只刷新 Git 分支、暂存区及本次相关差异。缺少上下文时才补读适用 AGENTS.md、ROADMAP.md 或相关知识，不因进入 push 阶段重新加载全套资料。按任务归属和完成证据确定范围：
   - 用户明确指定范围时，按指定范围执行。
   - 未指定范围时，先识别待提交改动对应的任务，并结合实际产物、必要验证及当前进度判断完成状态，不仅凭文件名、dirty 状态或旧完成声明判断。
   - 这些任务均已完成时，纳入全部已确认归属的改动；多个任务按任务／主题分批提交，有依赖时按依赖顺序提交，不要求用户额外说“全部”。单个已完成任务直接提交。
   - 存在未完成任务时，退回仅提交本次任务，不顺带提交其他已完成任务。当前任务自身未完成或必要验证未通过时，不自动提交半成品，说明未满足项。
   - 归属或完成状态不明的改动不视为已完成，保留并退回本次任务；本次任务仍无法确定或无法隔离时，只澄清缺失信息。仓库外的历史待办不自动算作本批改动中的未完成任务。
   执行前简述任务分组、完成依据、选定范围及保留项；范围可确定时直接继续，不重复确认。
2. 确定每批风险档位与必要检查，沿用当前任务已掌握的上下文，不为 push 重新审计项目。低风险必须同时满足：范围与完成证据明确、改动局部且不改变行为或公共契约、无混合暂存／并发变化、相称验证已通过或能直接补齐。多批相互独立且均满足条件时，也可走低风险。其余走标准档，只复核具体风险涉及的部分。场景有疑问时按需查 [push 场景与检查](references/push场景与检查.md)，不把场景表当作每次必跑清单。

## 检查归属与复用

- 每项检查只执行一次：已有结果与当前内容、依赖、配置、输入及环境仍等价时复用；新改动、失败或具体疑点只使受影响检查失效。写入前核对已确认范围是否漂移，不重新猜任务归属。
- 两档均保留最低检查：实际暂存差异与允许范围一致、文件名及内容的敏感信息检查、差异格式检查、项目必需及本次相关验证、待推送提交集合与目标、提交后文件范围和剩余改动、远端提交可达性。不为普通文案新增测试，不因低风险跳过项目必需门禁。
- 普通错字、标点等纯文案，最低路径是局部 diff／敏感信息／格式检查 → 精确暂存并核对 → commit → push → 一次远端确认。无受影响行为且没有明确适用的强制门禁时，不跑全仓 lint、类型检查、构建、测试、浏览器验收或新建测试；一般性的“做相称检查”不等于“跑所有检查”。UI 与重命名只补受影响的渲染／引用检查，已有等价结果直接复用。
- 独立只读查询可合并执行，写入按依赖顺序执行并检查退出码；异常停止对应写入。检查只覆盖选定差异及直接依赖，不扫描无关文件，不跳过已有 Hook 或项目明确适用的门禁。
- 标准档在外部推送前核对具体风险涉及的实现、直接调用方及相关验证，已有等价证据可复用。发现新风险时保留现场，定向处理后续跑，不重启整套流程。确有独立审查需要时按适用审查与委派规则处理，不因标准档自动派发；提交及推送仍由主 Agent 收尾。

## 主 Agent 直接执行

- 使用当前会话的终端工具直接执行 Git，不生成委派工作单、模型输入文件或交接报告；参数安全传递，用户文本不得拼接成 Shell 代码。沿用现有登录、权限和 Hook，不添加绕过开关。
- 写入前重新核对 HEAD、分支、工作区和远端，发现并发变化先对账。检查本次暂存区的文件名及内容，拒绝真实环境配置、密钥和私人数据；无密钥示例模板按项目规则允许。
- 精确暂存任务范围，禁用 `git add .`、`git add -A`。保留已有无关暂存；不能可靠隔离时停止并返回具体冲突。提交使用 `TZ=Asia/Shanghai git commit`，中文说明，前缀按全局／项目 Git 规则，不加 Co-Authored-By。提交后核对实际差异；Hook 改写文件、引入额外改动或检查失败时停止后续推送，不能绕过 Hook、自动带入或复用已失效验证。
- 只向已确定的远端／分支普通 push，不创建 PR、不发评论、不部署、不 tag、不 force-push、不 reset／clean／rebase。远端目标缺失或含尚未授权的历史提交时返回说明；push 拒绝或结果未知先查远端，不盲目重试或改写历史。
- 推送后读取 `git ls-remote` 的目标分支 SHA；等于已推送 HEAD 时确认成功。远端随后前进时，取得必要远端对象并验证已推送提交是目标分支的祖先；无法确认则标记结果待核实，不能仅凭 SHA 不等断言失败或重推。无改动但有已授权本地提交时只推送；没有任何待交付内容时不制造空提交。
- 保留精简证据：每批提交 SHA 与文件／片段范围、检查对象及通过／复用／失败状态、必要命令结果摘要、推送目标与远端 SHA／可达性、剩余改动及 CI 状态。无需另建报告；没有证据的项标记待核实。

## 分级验收与交付

- **低风险**：必要检查与远端确认完成即交付，不在收尾时再次读全量 diff、重跑测试或查询同一远端。证据缺失或矛盾时只补查缺口，必要时升级标准档。
- **标准档**：核对实际提交与推送前已审范围一致、远端结果及剩余改动；不重做已完成且仍等价的实现检查，不扩成全仓审计。
- 普通 push 以授权范围正确、适用本地检查通过且远端已收到为交付点。已知无相关 CI 时不查询；有相关 CI 时由执行者查询一次，不轮询等待。只有项目明确把 CI 终态列为本次交付门禁，或用户要求等待／修复 CI 时才等待并按该任务验收。pending、未触发、查询失败分别如实报告。
- CI 失败时读取失败步骤或摘要，区分测试断言／构建问题和依赖、权限、网络等环境问题；证据不足标记原因未定。远端失败不抹掉本地通过的记录，本地通过也不能证明远端正常。普通 push 不自动扩展成 CI 修复任务；可报告“推送成功，CI 失败”后交付，明确失败项及未验证范围，不能称全部验收通过。明确适用的发布门禁失败仍阻止发布。
- 简短交付提交 SHA、推送结果及必要异常。任务进度已准确时不为一次机械提交新增计划、检查报告或改写 ROADMAP；确需同步实质状态则只更新一次，不为重复记录 SHA 制造收尾提交循环。
- 速度看是否消除了模型交接、等价重复检查与全量重读；质量看范围无越界、必需检查有证据、远端结果可核实。耗时异常时记录实际等待点，不设到时跳过检查的硬阈值，也不凭规则修改宣称已提速。

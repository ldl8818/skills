# 升级与定制合并

更新 Skill、插件或其执行依赖，处理本地定制，或设计使用时更新提醒、托管维护和中断接续时读取。来源、完整源覆盖和路由字段的完成条件归 [SKILL.md](../SKILL.md#更新的完成条件)，本文件补充判断与执行流程；冻结集合的固定来源、许可和登记命令归 [冻结版本维护](冻结版本维护.md)。

## 职责与当前能力

| 层次 | 职责与边界 |
|---|---|
| 状态与对象解析 | 使用 `core.py` 的真实路径、作用域和来源记录，保证检查、帮助、验证、更新及执行指向同一对象。 |
| 现有更新脚本 | `update_skill.py` 支持来源与通道识别、机械三方合并、冲突保护、完整性检查及在线目录切换；`--dry-run` 的范围以当前帮助为准，不代表已生成候选或完成语义审查。 |
| 合并与验收工具 | `merge_bytes`／`merge_skill_dir` 可生成合并草稿；`audit_upstream.py` 核对完整源、字段与回执。文本无冲突和哈希一致均不证明定制已被上游支持。 |
| 执行维护的 Agent | 清点定制用途，比较旧上游、本地与新上游，作语义判断，完成兼容适配和行为验证，并报告实际结果。 |
| Lookup 的执行委派 | `lifecycle.py` 按真实安装路径接入检查、单项和批量；总更新及限定本体／上游均调用 Lookup 同一维护器。旧版缺接口时报告具体缺口，不能按 local 静默跳过；对象与范围协议归 [Lookup 更新说明](../../lookup/references/上游更新.md#命令与范围)。 |
| 使用时提醒与托管 | 当前 skill-manager 通过显式 `check`／`update` 执行维护。下文的缓存、通知去重、按依赖托管及可恢复事务要求，适用于已有接入或后续实现；它们不表示本 Skill 已新增后台服务、托管开关或接续命令。 |

命令、自然语言及已授权托管采用相同的来源、定制和验收要求。现有脚本不能独立作语义判断；存在执行或业务定制时，Agent 先在隔离目录完成判断、合并和相称验证，再应用结果。不得直接执行机械更新后，凭脚本成功输出宣布定制审查完成。

## 检查、提醒与维护授权

- 普通使用只进行已接入的只读检查和提醒；明确要求更新或已按依赖开启托管，才执行对应维护。实现更新能力不等于开启托管，冻结或固定来源也不因发现新版而解除。
- 优先复用上游可靠的只读版本检查与现有缓存，避免重复请求。接入使用时检查时，设定成功缓存、失败重试间隔和同一目标版本的通知去重；检查失败不阻断原任务，也不报告为已是最新版。
- 原生命令若包含下载、安装或重启，不用它探测远端版本。缺少可靠的只读接口时，报告检查边界；本机版本变化与远端有新版分别处理。
- 提醒与业务输出分开；新检查未返回时先完成原任务。托管在本任务资源释放后执行，维护前告知对象和必要影响，维护后报告结果。重复使用不能重复安装同一失败版本或扩大授权。
- 默认沿用已选择的发布通道、安装来源、管理器、环境和固定版本策略。托管另行定义可接受版本范围、观察期及失败重试条件，不能单靠版本号判断兼容。用户明确选择的 `main` 通道仍按其通道维护。

## 定制判断与合并

1. **核对实际对象。** 确认当前有效入口、真实源码、客户端加载路径、选定通道和原安装环境。显式可执行文件覆盖、同名多份安装和管理器目录都要与执行入口一致，不能更新另一份后报告生效。
2. **清点所有定制。** 检查包内补丁、独立 Skill、用户覆盖、插件、调用封装、本地独有文件和授权／路由约束。即使安装器未改写独立 Skill，也要判断它是否仍遮蔽新版能力；列表没有 dirty 标记不代表没有相对上游的定制。
3. **建立完整依据。** 在隔离目录保留完整旧上游、本地现状和完整新上游，核对来源、确切版本或 commit、文件清单及内容指纹。安装清单或发布包摘要可帮助核验原始内容；版本标签、本地当前内容或安装器输出不能单独充当原始上游。未知旧／新源先恢复对应官方快照，不能修改登记哈希来绕过缺口。
4. **逐项判断行为。** 对比定制的用途、调用方、参数、权限、结果及失败边界；上游可能通过不同文件或不同实现提供同一能力。按下表处理，不能把逐字相同作为采用新版的前提，也不能把“本地定制”作为永久保留旧实现的理由。
5. **以完整新上游生成结果。** 采用已支持的原生实现，只合入尚需的最小定制；同步处理新增、修改、删除及本地独有文件。上游路由字段仍按入口要求保留完整原文；替代实现不能成为删改字段、许可、来源或有效约束的理由。
6. **验证后再应用。** 对已吸收的定制验证等价行为，对保留的定制覆盖原失败及相邻正常路径，同时验证新版新增能力没有被旧补丁遮蔽。完整源检查、脚本测试、真实客户端与账号业务分别报告。只有相关检查通过，才更新来源基线及合并回执。

| 判断 | 处理 | 所需依据 |
|---|---|---|
| 新上游已完整支持 | 采用新原版；移除已无用途的覆盖、重复封装或本地文件，并核对引用。 | 新实现的位置、调用关系，以及覆盖原用途和失败边界的等价行为验证。 |
| 新上游尚未支持 | 保留必要定制，适配到新上游完整实现；保持新版新增能力。 | 仍缺少的具体行为、最小适配理由，以及定制和新版正常路径的验证。 |
| 部分支持或存在冲突 | 按行为拆分，采用已支持部分，合入仍需部分；无法确认时保留当前有效内容。 | 每个行为的判断、剩余差异和明确的待核实项。 |
| 来源或原始基线未知 | 先恢复依据，未恢复前保持当前内容和具体阻塞。 | 确切原版本／目标版本及完整源，不能将本地定制登记成纯上游。 |

每项判断记录定制用途、处理结果、具体源文件／接口依据、实际验证和最终适配；一个文件包含多项行为时分别说明。已被吸收的定制也要记录采用原版的理由。现有 `upstream-merge.json` 的完整性验收继续使用其既有格式；机械生成的适配说明不能代替本轮语义依据，不能复制示例中的测试结果冒充实测。

## 候选、切换与接续

- 帮助或指南读取会改写配置时，使用隔离 HOME。候选验证包含实际需要的覆盖、插件和配置上下文；因占用延后后复用候选，仍使用同一上下文，不先拿空环境验证已依赖定制的候选。
- 切换前重新核对目标、完整旧／新源、本地现状及合并结果。任何内容漂移均使旧判断失效；保留旧材料，以最新本地内容重新比较并验证，不编辑回执哈希来忽略并发修改。
- 需要可恢复升级的执行器须持久化目标、原有效入口、阶段、源快照、候选、验证及恢复位置；这些材料属于本机维护状态，不进入公开仓库。接续先查当前实际状态，不能仅凭上次进程退出、命令返回0或版本增加判断完成。
- 将“运行程序更新”“独立 Skill 合并”“行为验收”分别核对。原生操作仍在等待、超时或结果未知时，不能因 Skill 合并完成就报告升级成功；没有完成证据不重发结果未知的动作。固定来源不能达到目标时保留并报告，不悄悄换源。
- 原生安装器可能直接改动在线内容时，先保存原状态。恢复前保存每份不同的实际内容及指纹，包括等待、失败和并发编辑产生的内容；复制期间再次变化时停止恢复并保留现场。安装后观察内容作为合并依据之一，不能未经核实就称为纯上游。
- 按执行器能力使用锁、延后切换或原子替换，保护正在使用的对象。只回收本次创建的进程和资源，不以停止共享服务解决占用。已授权的常规恢复连续处理，用户接管或权限拒绝时停止相关动作。
- 回滚前核对原目标的完整内容指纹及相关覆盖；路径、版本号或主文件一致不代表整套旧环境仍相同。原目标被其他维护改变时保留恢复材料并重新核对，不能覆盖新的用户修改或误报已恢复。

脚本只给出待判断材料时，执行维护的 Agent 在已有授权内继续比较、适配、验证和接续。冻结、冲突或缺少自动能力本身不构成任务完成；确实无法恢复来源、缺少业务环境或需要用户作关键决策时，报告具体缺口与已保留内容。

## 定向验收

按改动影响选择场景；下表用于走查或设计验证，不表示已经完成某个执行器的自动化测试。

| 场景 | 核验结果 |
|---|---|
| 新版通过不同代码覆盖定制 | 采用新原版，原失败及相邻输入得到等价结果，重复覆盖退出实际生效路径。 |
| 新版只覆盖部分定制并增加能力 | 所需旧能力仍在，新能力通过；例如保留空值，同时采用新版分页或数字解析。 |
| 安装器未改写独立定制 Skill | 仍核对新源与定制用途，不能仅凭目录未变或包已升级销项。 |
| 已合并候选因占用延后 | 接续复用正确候选及相同覆盖／插件，验证通过后再切换。 |
| 原生等待或结果未知 | 状态保持未确认，先读回原操作；Skill 合并与命令退出0不能提升为成功。 |
| 判断后并发改动或升级中独立编辑 | 旧判断失效；新增内容及恢复入口仍可找到，重新核对后才应用。 |
| 原恢复目标的非主文件被修改 | 完整指纹检查阻止误回滚，不覆盖其他维护的新内容。 |

需要验证真实 Agent 决策时，使用完整合成快照和隔离执行器，让评估者自行比较、生成实际依据并接续；验收有效入口、合并结果和行为样本，不能只采信“已完成”的文字。安装、迁移或入口变化另在干净 HOME 实跑；隔离结果不代表其他机器、真实账号或自然使用已验证。

## 1．目标与边界

新机按官方方式安装必要软件，恢复选定的配置、规则、Skills 与知识，在新机验证能继续日常 AI 工作。优先复用已有工具和资产来源，仅补足逐项安装、检查、失败处理及续跑。

当前已授权开发、隔离验证与相关来源维护；旧机现役配置不自动应用，真实新机安装、登录和任务启用按目标机阶段执行。

### 纳入范围

| 对象 | 处理方式 |
| --- | --- |
| Codex、Hermes CLI | 按各自官方推荐渠道安装，检查路径、版本和基本运行；本次不安装 Claude Code |
| 必要前置 | Ghostty 作为用户日常终端优先安装；仅安装选定 AI 工具或工作项目需要的 Command Line Tools、Homebrew、Shell 设置、Node、Python、uv 等；保留合理的现有运行时管理方式 |
| AI 配置与规则 | 选定的配置、AGENTS.md、角色／Profile、Hooks、MCP、Plugins、Skills 及其接线；先核对来源和新机路径，再应用 |
| 经验与知识 | Doraemon 私人知识库、用户维护的经验和规则、选定的 Hermes 记忆、需要的 Obsidian 笔记与附件；保留原有归属，不重新设计记忆体系 |
| 凭据 | 按客户端要求重新登录；确需传递的 API key 等走已有加密或密码管理方式，不进入公开仓库、报告和日志 |
| 工作项目 | 仅用户选定项目；正常代码从 Git 获取，本地独有提交、未提交文件和必要本地配置单独列出并处理 |
| 辅助应用 | 仅选定的终端、编辑器、Obsidian、必要网络前置等；不按旧机应用全集自动安装 |

配置和知识不一定都要先复制到同一个包里。每项使用一个明确来源：已有配置仓库、知识库同步渠道、Git 仓库，或一次性加密传递的必要文件。

### 明确排除

- 整机备份或整机恢复，以及把 Time Machine 验证设为换机流程门禁。
- 全盘扫描、系统级偏好全集、浏览器数据、Keychain／TCC 数据库和登录态批量复制。
- 离线客户端封装、安装包镜像、所有软件的固定字节复现、随包分发 Python 等便携运行时。
- 通用 Git 备份引擎、自动保存全部工作区、自动解决冲突、清理旧机或删除数据。
- preview／final 双模式、全局冻结与解冻、双故障域副本协议、业务游标对账和自动回切框架。
- 为换机统一包管理器、升级所有软件、重构 AI 架构，或增加长期配置同步服务。
- 缓存、node_modules、旧 venv、派生索引和编译产物；普通历史会话不默认迁移。确有继续旧会话需求时单列，不当作正式知识。
- OpenClaw：不安装、不恢复、不继承其凭据。

旧机在新机验收前保持原样可用。需要退出某个应用以安全复制其选定文件时，只处理该应用和复制窗口，不把它升级成整机停机事务。

## 2．复用方式

### 首选：已有 chezmoi＋官方安装方式＋必要文件传递

- **chezmoi**：继续管理已纳入的配置、路径模板和软链。先检查仓库源与现役文件是否有差异，避免恢复陈旧配置；不批量收编整个 HOME，不无条件全量 apply。
- **Homebrew Bundle**：管理精简且经过选择的工具／应用清单。安装前检查已有软件，避免重复安装和未经选择的升级；不把官方 CLI 安装渠道强制改为 Homebrew。
- **产品官方安装器**：Codex、Hermes 按执行时核对过的官方方式安装。工具负责编排与检测，不重写安装器、不自造包；Claude Code 仅保留显式选择的兼容接口。
- **已有知识同步／Git／加密传递**：分别承担知识、代码和必要私人文件的取得，不另建通用归档协议。
- **现有分步骤入口**：优先评估 dotfiles 仓库的 status／plan／apply-step 结构，补缺口即可；不同时维护两套相同职责的恢复器。

现有 chezmoi 脚本会进入 Hermes 网关加载步骤，其状态检查也不能代表所有 AI 组件已就绪。后续复用前，必须把“安装／应用配置”与“启动业务任务”分开。不能直接把现有全量 apply 当作本方案入口。

Dotbot 可作为轻量组织方式参考，不为本次换机替换 chezmoi。Mackup 的 copy 模式仅在确有选定应用设置缺口时考虑，不默认引入。Ansible 类整机配置方案不纳入本次实现。

## 3．只维护一份私人清单

逐项记录：对象、是否必需、当前来源／版本、安装方式或待迁移文件、新机目标、检查方式及当前结果。清单存放在私有位置；公开文档只使用合成示例。

- 扫描仅限已知 AI 配置入口与用户选择的项目／知识根，不为枚举整台电脑建设覆盖账本。
- 可重建软件只记安装来源和必要版本约束；不可重建内容明确列出。
- 当前安装方式只作为观察事实，须与官方支持方式核对；发现多个可执行文件或管理器冲突时展示差异，不悄悄切换。
- 知识及配置分清真身、模板、软链和生成物；生成物在新机重建。
- 私人文件可以正常迁移，但不因此进入公开 Skill 仓库。审核记录不伪造，新机路径改变引发的知识复核按 Doraemon 现有规则办理。
- 选定项目的本地独有内容不能遗漏；遇冲突索引、LFS、子模块或外部 filter 等特殊情况，列为该项目人工项，不阻断无关 AI 环境准备。

不要求用户填写多套 profile、安装缓存索引、任务协议和副本凭证。

## 4．从第一次打开新 Mac Mini 开始

以下是用户流程，当前本地引导的启动方式见使用说明。默认用户已完成新 Mac 的账户设置和网络准备；网络工具的安装由用户自行完成，本文不展开。

确定的默认顺序：**Homebrew → Ghostty → GitHub 与配置来源准备 → AI 客户端 → Obsidian 与知识库 → 配置和经验接入 → 验收**。

AI 客户端与 Obsidian 没有强制安装依赖，技术上可以同时安装。本次引导默认串行，先安装 Codex、Hermes，再安装 Obsidian：尽早让 AI 客户端具备基本使用条件，也便于定位安装失败；不为节省少量等待新增并发安装调度。Obsidian 不阻断客户端基础启动，知识目录就绪才是完整知识接入的前提。Ghostty 是用户选定的基础终端，不是 AI 软件必需的运行依赖。

### 出发前：旧机只做一次材料检查

引导列出用户现有的配置仓库、Obsidian GitHub 仓库、选定 AI 软件与知识目录，请用户确认。

- 核对 Obsidian Git 的实际自动设置，不把“已配置自动同步”当作“所有文件已经上传”。检查未提交修改、本地独有提交、忽略文件和远端分支。
- 正式传递前，在旧机完成必要提交与推送并核对远端；该外部写操作在实际迁移阶段按授权执行，本次方案编写不代为提交。
- chezmoi 核对已登记的配置及其源／部署差异，列出尚未纳入但可能需要的隐藏文件。发现文件不等于必须迁移。
- 用户只需准备账号登录／解密方式，记住要恢复哪些仓库。私人仓库地址、实际插件设置和真实文件路径不写进公开方案。

### 第1步：打开引导，先把前置装好

用户打开 macOS「终端」，使用本地交付的 setup.command。入口先用 macOS 自带 Shell 和系统工具运行，不要求先安装 AI 客户端、Homebrew、Python 或 chezmoi；不使用旧 final 恢复命令。

屏幕逐项显示“已就绪／正在安装／需要你操作／失败原因”：

1. 检查系统、必要网络访问和 Command Line Tools；缺少时调用官方提供的安装流程，等待系统安装完成。普通用户无需先装完整 Xcode。
2. 检查 Homebrew。先查 PATH，再检查 Apple Silicon 的标准安装位置；已安装但 PATH 未生效时修正接线，不重复安装。
3. 真正未安装时，调用 Homebrew 官方安装方式。系统密码或确认由用户按官方提示完成，不承诺完全无人值守。
4. 安装后核对 brew 的实际路径、版本和 shellenv 接线；验证新终端能找到它，再继续。前置失败就停在该项，修复后重开同一入口续跑。

这就是“缺前置便先安装”的机制。Homebrew 在这条引导中用于安装必要工具和应用，不代表每个 AI 软件都依赖 Homebrew，更不应提前安装所有 Node／Python 版本。

### 第2步：安装 Ghostty，在日常终端中继续

Homebrew 就绪后检查 Ghostty，缺少时通过其官方支持的安装渠道安装，已有可用安装直接复用。继续在原终端完成向导，结束后再使用 Ghostty；中断后同入口检查已有结果继续，不从头重装。

检查 Ghostty 中能否找到 brew、Shell 启动是否正常。Ghostty 的配置、字体依赖和快捷键纳入私人清单，逐项核对是否已经由 chezmoi 管理；目前不能假定已覆盖。缺少自定义配置不阻断默认终端使用，后续定向恢复。

### 第3步：准备 GitHub 登录与配置来源

按需准备 Git、GitHub CLI 和 chezmoi。引导用户登录有权限的 GitHub 账号，检查 Git 认证可用，再取得已确认的 chezmoi 配置仓库；此时只检查内容和待应用差异，不全量 apply。

GitHub 登录和 Git 提交身份是两件事：提交姓名／邮箱从选定配置恢复或由用户填写。Shell 与 AI 配置、知识库分别保留自己的来源；不要因为下载了配置仓库，就认为知识库也已取得。仓库认证失败不阻断无依赖的官方软件安装，但依赖私人文件的配置步骤暂停。

### 第4步：先安装 AI 客户端

按本次选择，依次通过官方方式安装 Codex、Hermes，不安装 Claude Code。仅在对应软件要求时补齐 Node、Python、uv 等依赖，不预装所有运行时，也不把旧机 venv 搬来。

每装一个就检查可执行文件、实际版本和基本启动。安装成功不等于已配置或已登录。需要尽早使用客户端协助后续步骤时，可先完成其必要登录或最小连接配置；不依赖知识库的配置可以提前定向应用，依赖未恢复路径的 Hooks／知识接线暂缓。用户原有规则和经验要到第6步完成接入后才能验收。

### 第5步：安装 Obsidian，恢复知识库

检查 Obsidian 是否已安装，未安装时使用官方 Homebrew cask 中的 Obsidian，已有可用安装直接复用。不连带安装整个旧机 Brewfile。

这时装好的是 Obsidian 应用，笔记还没回来。引导接着取得知识库并打开它，不把软件安装成功显示成资料恢复成功。

#### 选择存放位置，从 GitHub 取得知识库

默认方式为 **GitHub 克隆**。引导只让用户做两件事：登录有仓库权限的 GitHub 账号，以及选择知识库在新机上的文件夹。

- 私有仓库先完成 Git 凭据配置；可使用官方 GitHub CLI 的浏览器登录流程，并检查 Git 的认证是否可用。Git 提交姓名／邮箱另行从用户选定配置恢复或填写，GitHub 登录不等于配置了提交身份。
- 引导带出已确认的仓库地址和分支，在用户选择的空目录中克隆；目录已有内容时让用户选择已有仓库或改选目录，不覆盖。
- 克隆后检查分支、远端、笔记与附件，以及被 Git 跟踪的 `.obsidian` 配置和插件文件。Git 忽略或尚未提交的文件不会随克隆出现，必要项目单独补齐。
- 首次打开前确认配置中没有旧机失效路径或会自动执行不期望动作的插件接线；不重新设计整套插件系统。

用户不需要在空白 Obsidian 窗口里手工填写 GitHub 地址。先由引导克隆成一个普通本地文件夹，再打开它，步骤更直接。

#### 在 Obsidian 打开知识库，恢复自动同步

用户在 Obsidian 的仓库管理界面选择 **“打开文件夹作为仓库”**，选中刚克隆出的文件夹。不是新建空仓库，也不是选择它的父目录。新机可以选择自己的目录，不必沿用旧机用户名或绝对路径。

- Obsidian Git 是社区插件，和付费的 Obsidian Sync 是两种独立同步方式；本流程沿用已有 GitHub 方式，不要求购买 Obsidian Sync。
- `.obsidian` 中被跟踪的插件及设置随仓库取得；若缺少插件，按官方社区插件入口补装。首次打开按 Obsidian 的提示确认信任，再启用需要的插件。
- 显示旧机实际的“启动拉取、自动提交／同步、间隔、推送”设置，按用户原有习惯恢复，不凭插件默认值猜测。启用自动同步前先确认认证和提交身份。
- 先检查笔记、附件和一次手动拉取。需要证明新机写回 GitHub 时，明确执行一条用户授权的测试修改，完成提交／推送并从远端核对；未执行就标为“推送待验证”。
- 平时通过 Obsidian Git 自动提交和同步；两台机器都要编辑时先拉取再修改，遇冲突停下来处理，不能自动覆盖。此处只说明知识库协作，不引入业务冻结机制。

#### 可选：用 U 盘带来知识库

大附件较多、下载慢或还有大量未进入 Git 的必要内容时，可选择 U 盘；不把它作为所有用户的必经步骤，也不宣称一定更快。

1. 旧机保存笔记并退出 Obsidian，完整复制选定知识库文件夹；要保留后续 Git 同步时必须包含隐藏的 `.git` 和 `.obsidian`，只复制可见 Markdown 不够。
2. 新机先将文件夹复制到自己的本地磁盘，检查文件完整性，再在 Obsidian 中打开；不直接把 U 盘作为长期编辑位置。
3. 新机仍需重新完成 GitHub 认证，检查 remote／分支和本地未提交内容，与远端比较后再同步。复制仓库不代表已登录 GitHub，目录内的旧凭据也不能当作新机认证方案。

GitHub 克隆和 U 盘复制二选一作为首次取得方式，不向同一个已有目录反复覆盖；已有资料不清空重来。普通 GitHub 仓库的“Download ZIP”不含 `.git`，不作为保留 Git 同步的默认途径。

### 第6步：应用配置和经验

AI 软件与知识目录就绪后，从第3步已取得的 chezmoi 仓库预览差异，定向应用尚未完成的配置；提前应用且检查通过的项目不重复覆盖：

- Ghostty：核对配置、实际字体依赖和快捷键；按已确认的管理来源恢复，字体缺失时只补需要的字体。
- Shell：核对 `.zshrc`、`.zprofile`，以及实际存在的 `.profile`、`.bash_profile` 等。不能把“主要 Shell 配置已登记”扩大为“所有隐藏文件都已覆盖”；无关旧入口不自动搬入。
- AI：恢复选定配置、规则、Profile、Skills、MCP、Hooks 与必要链接；路径模板按新机 HOME 展开。
- 知识：Doraemon 指向已经恢复的私人知识目录，让客户端按需读取；按现有机制完成检查与必要复核。不把整个知识库复制到 Codex 配置目录，不维护第二份经验副本。
- 凭据：需要重新登录的客户端引导登录；已有加密配置按需要解密，不输出秘密。

现有 chezmoi 的自动脚本含网关启动步骤，不能直接全量 apply。后续实现必须先排除这些启动动作，再把选定配置接入本流程。初次 Homebrew 接线和之后 chezmoi 的 Shell 模板也要一致，避免应用配置后 brew 又从 PATH 消失。

### 第7步：看结果，开始使用

用户最终看到的是逐项结果：前置已就绪、Obsidian 知识可读且同步状态明确、各 AI 软件能用、规则与经验可读取，未完成项有具体下一步。

必需项通过后即可开始日常工作。私人清单选定的 Hermes 网关必须完成切换、启用与验收；未选定的定时任务和其他外部业务入口另列为“尚未启用”，不自动启动。中途关掉终端或某项失败，重新打开入口检查当前状态，从未完成项继续。

## 5．安装、失败与续跑规则

每个软件遵循同一顺序：**检查现状 → 确定官方方法 → 安装 → 检查结果 → 继续下一项**。

- 已安装且满足要求时直接复用，不重复安装。
- 使用执行时核对过的官方文档；允许官方安装器正常联网及处理依赖，不将其拆成自维护的离线安装过程。
- 安装命令退出0不等于完成。重新查实际可执行文件、版本与基本启动，必要时提示重开终端使 PATH 生效。
- 记录旧机版本和新机实装版本。有明确兼容要求时使用官方支持的版本选择；官方不支持旧版时展示差异并检查配置兼容性，不为追求相同字节自行打包，不静默换版。
- Homebrew 的不升级选项不能锁定新机版本。已有合理运行时管理方式不强制替换。
- 下载、网络、权限、PATH、版本不符、部分安装、待登录分别给出具体结果和下一步；只在原因明确后重试，不循环盲装。
- 失败只阻断依赖该项的后续步骤，独立项可继续；必需项失败不能显示整体完成。
- 续跑重新检查实际状态，已成功且仍满足要求的步骤跳过；记录不能代替现状检查。无需自研全局事务引擎。
- 登录、管理员密码和系统权限通过产品或系统正常交互完成。官方安装器若会启动服务，使用其支持的跳过方式或停在人工步骤，不绕过这一行为。

## 6．必要保护与定时任务

保留直接服务于此次换机的保护：

- 覆盖前展示具体文件差异；已有内容冲突时停止该项。确需修改时保留受影响文件的可恢复副本，不做整机备份门禁。
- 敏感文件使用已有加密传递方式，限制权限；校验传递后的内容是否完整，不在日志中输出秘密。
- 只修正选定配置内已知的旧路径，不全盘替换用户名；不盲目执行迁移文件中携带的命令。
- 旧机数据不删除，不因新机某项失败清空已恢复内容。

私人清单选定的 Hermes 网关及对应角色属于迁移必需项：先恢复配置、记忆、渠道授权和必要启动服务，安装配置阶段保持未启用；确认旧机对应网关停止后，在新机启用并逐个验收。失败时先确认新机停止再恢复旧机。未选定的 cron 和其他业务任务不随网关启用。复用既有受控入口，不开发通用防重、游标或回切系统；当前基础 setup 的成功不能代替网关验收。

## 7．验收与交付

### 工具实现验收

- 覆盖已有安装、全新安装、下载失败、部分安装、PATH 未生效、版本不符和重复执行。
- 验证选定配置冲突停止、不同 HOME 路径、必要文件完整性，以及秘密不出现在报告中。
- 验证失败后续跑不重复成功步骤、不自动启动任务、不破坏新机已有内容。
- 在干净 HOME／合适的隔离环境按文档走通安装与配置流程；涉及系统安装行为时使用适当隔离环境，不能靠更换 HOME 宣称系统已隔离。
- 模拟安装器测试只证明步骤控制。真实官方安装过程和真实新 Mac 验收必须单独记录，不能由旧工具测试数量替代。

### 新 Mac 实际完成标准

1. 用户选定的必需软件能启动，实际路径与版本明确。
2. 被选为必需的 AI 客户端分别读取应有的配置、规则和知识；Doraemon 被选为必需时，完成现有安装检查及对应客户端接线验证。未选中的客户端不安装、不验收，也不阻断完成。
3. 选定知识库可打开、必要附件可读取；如果选定了工作项目，至少一个选定项目能继续使用。未选项目时不为验收强行增加项目迁移。
4. 必要登录完成；需要真实外部或付费请求才能验证的能力，按具体授权执行，否则明确列为待验证。
5. 未启用的定时任务明确列出，不能误报为已经接管；它们不阻断基础环境完成。
6. 报告只列已通过、失败／待处理、待登录／待验证及未迁移项，必需项未通过时不宣称完成。

最终交付是：一份私人迁移清单、最少的分步骤引导／检查改动、必要资产的取得方式、简短操作说明和逐项结果。无需完整自包含迁移包、双盘证明或业务演练平台。

新 Mac 尚未就绪，当前不能完成上述实机验收。

### 用户如何取得与继续引导

交付形态是一份普通的、只含引导脚本及必要辅助源码的目录和一页操作说明，不含客户端安装包、凭据、笔记或 Python 运行时。用户在新机浏览器取得已交付版本，或者用 U 盘带来同一目录；不要求先装 Git 或登录私人仓库才能取得第一阶段脚本。

操作说明提供一行下载、语法检查与启动命令；手动下载或 U 盘仍为备选。路径含空格必须正确处理。只有实际发布了相应版本，才能声称公开命令可用；未获发布授权时交付本地目录并标明待发布。

切到 Ghostty、重开终端或安装中断后，运行同一个 `setup.command`：第一阶段重新检查已装前置，满足条件就跳过，再进入 `bin/restore` 的新机流程。脚本不整体重复执行 chezmoi apply，也不重置 chezmoi 的 run_once 记录。首次取得私人仓库需要用户登录并输入或确认仓库地址，秘密不通过命令行参数传递。

第一阶段按实际安装状态续跑，不另建事务日志。后续流程在 `~/.config/mac-setup/state.json` 保存一份清单与简短逐项结果，目录权限0700、文件0600，拒绝保存到 Git 仓库或写入秘密。结果与当前机器和选定目录绑定；每次续跑重新检查。目录变化或文件冲突时更新计划并处理该项，不覆盖旧目标，不设计 session／副本协议。最终说明必须给出这个私有文件的实际位置和同一个续跑入口。

### 首次实现必须完成的清单核对

- 默认必需项：Homebrew、Ghostty、Codex、Hermes、Doraemon、Obsidian 知识库、10个网关与现有 chezmoi 配置恢复；不选 Claude Code 和工作项目。Git 等按依赖补齐，安装与验收使用同一份选择，不静默降级。
- 给每个选定文件注明源仓库条目或其他明确来源、目标路径、是否包含秘密、是否已经由 chezmoi 管理，以及应用后的检查。Shell、Ghostty 配置／字体／快捷键、客户端配置、规则、Skills 与知识路径都用同一张清单，不新建多套表。
- 核对 `.zshrc`、`.zprofile` 和实际存在的其他 Shell 入口；未纳管项先判断是否仍有用途，再决定纳管或明确排除。旧配置源有漂移时保留并报告，不自动以仓库版本覆盖现役文件。
- 将会启动网关、cron、launchd、业务脚本或引用未恢复目录的项目明确排除在新机自动应用之外。按具体目标选择配置、排除自动运行脚本；首次整体 apply 或先启动后停止均不可作为替代。
- 在本地核对每个软件执行时的官方安装来源、必要依赖、检测方式和服务启动行为，形成实现所用的固定步骤。私人清单不能提供任意 Shell 命令供工具执行。

| 检查点 | 交付结果 | 必须覆盖的验证 |

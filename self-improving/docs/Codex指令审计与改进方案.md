## 实际痛点与可验证目标

需求提出者描述了两类同时存在的顾虑：小范围任务被过度检查，耗时明显；减少检查又可能让 bug 没修全、修错或引出新问题。提交几句普通文案曾被报告耗费约5至10分钟，但本轮没有逐段计时，不能把全部耗时归因于某一个 Skill。

目标包括：已授权任务不因换轮、压缩、插入问询或阶段完成而无谓暂停；普通提交不自动进入完整发布流程；修复覆盖有证据的影响链；适用的验证结果可以复用；任何完成声明都与实际证据一致。

不采用固定分钟数强行截断检查。只有检查对象和执行层次正确，耗时才有解释意义。共享逻辑的一行变化可能比多份普通文案的变化风险更大，文件数、行数和后缀都不能单独决定验证深度。

## 讨论过程与最终取舍

### 第一阶段：从具体停顿记录区分原因

先对两个已指定工程的近期记录做定向核对，再沿记录查适用规则，没有从未提交文件反推任务目标。

案例 A 是分批提交推送：此前已有连续交付授权，接力摘要也保留了授权；随后注入的旧启动提示却明确要求收到继续口令后才能执行命令，Agent 因而停止。该案例证明历史注入确有错误适用范围，不应简单归为模型懒惰。现用全局规则及接力文案已区分独立新会话和同一任务恢复，历史问题不重复列作现行缺陷。

案例 B 是迁移工具开发：阶段测试通过后，仍有安装、配置合并和事务接线等可执行开发工作，Agent 却结束了任务；缺少目标机只阻塞真实迁移验收。没有找到要求阶段测试通过后必须停止的规则。插入的规则优化又被接力摘要解释成替换原任务，需要纠正任务状态解释，不能靠降低迁移验收要求解决。

上述案例为脱敏归纳，不是原始 transcript 或逐字用户引语；不含真实项目代号、会话文件名、会话 ID 或账户信息。需要重放历史记录时，由拥有原记录访问权的评审者在私人环境完成，本文不替代完整历史证据。当前接力规则和实现分别见 S01、S14，不能把历史注入内容当作当前实现。

### 第二阶段：将用户顾虑转为检查边界

第一轮建议包括收窄确认、全库扫描、全文重读和固定输出要求。随后补充的核心要求是：修 bug 不能只看报错函数，也不能因小改动读大量无关文件；提交文案不应等同于全面工程验收。

由此确定三个判断：先识别改动影响什么，再选择检查；扩大检查需要具体失败风险或共享依赖证据；验证是否仍适用由输入和环境决定，不由是否进入下一轮决定。

### 第三阶段：独立专家从工程可靠性角度反审

独立专家读取 check、hunt、health、neat-freak、think 及相关说明，重点反驳可能过度简化的建议。主 Agent 同时核对配置入口、其他 Skill 和项目局部规则，再核对专家引用，没有仅凭其完成声明接受结论。

| 原先可能出现的简单处理 | 独立复核后的最终取舍 |
|---|---|
| Markdown 改动都走免测试路径 | 只限不改变行为或操作契约的普通说明；权限、路由、安装命令和执行流程仍需定向验证 |
| 已跑过一次就复用 | 必须核对被测内容、依赖、配置、生成输入及相关环境，且能定位真实执行证据 |
| 为减少工作取消红绿回归 | 保留修复前失败、修复后通过的区分能力，改用不干扰 WIP 的验证方式 |
| 限定局部修复就是只看一个函数 | 必须核对直接调用方、结果使用方和共享实现，证据支持时扩大 |
| 所有高耗时门禁都应删除 | 先区分 Agent 手动重复、提交钩子、本地检查和远端 CI；适用门禁不能绕过 |
| 文件存在或配置能解析就代表已生效 | 仅证明静态状态；会话加载、Hook 执行和实际行为需分别验收 |
| 项目存在严格规则就是错误 | 核对具体风险和明确例外；局部项目规则单独处理，不混入全局 Skill 修改 |

### 已纠正或不采纳的判断

有意保留的纽约 Shell 时区不与北京业务时区天然冲突，不再建议改动。首次私人扫描、真实迁移和业务切换确认有实际边界依据，应保留。已停用的 Skill、未加载缓存、示例中的虚构路径和历史版本说明不能直接算现役失效。全量枚举不等于全文读取。严格措辞的存在不能证明条款专为旧模型编写，也不能单独证明一次长耗时由它造成。

文档交付阶段另确认了命名偏好：后续新建文档使用中文文件名，产品名可保留。本文件因此采用中文名称；此项不构成批量重命名既有文档或改动代码标识符的授权。

## 证据分类、定位和覆盖边界

| 标签 | 含义 | 可作出的结论 |
|---|---|---|
| 明文 | 当前来源确实写有该要求 | 可判断指令本身的范围或内部矛盾 |
| 歧义 | 不同句子或作用域允许多种解释 | 可建议消除歧义，不能断言所有执行都如此 |
| 历史行为 | 已读取到相关授权、提示和任务结束记录 | 可说明该样本发生了什么，不能推及所有会话 |
| 静态核对 | 配置解析、入口存在、引用和源码文案核对 | 不能替代客户端实际加载或执行证明 |
| 待验证 | 尚无相应运行或耗时证据 | 不宣称改善已经生效或已节省特定时间 |

广范围审计盘点54个全局、系统或插件 Skill 入口，其中包含未加载缓存；重点条款按上下文复核。另检查 Codex 配置、Hook 命令入口、已登记工程的规则入口，以及两个指定工程的相关会话。并非对全盘所有目录、全部插件脚本、所有历史会话或第三方服务做完整安全审计。

没有读取凭据文件、执行安装或重放真实业务。现用 Hook 指向的已检查文件存在，配置可解析；未以此宣称每个事件已在当前客户端正常执行。

来源使用 S 编号，问题使用 F 编号，验收使用 T 编号。行号是审计快照定位，不是永久锚点；原句以代码样式或引用块保留，省略处明确用 `…` 标出。拟议替换使用中文，实施时可译为来源语言，但不能改变条件和边界。

公共定位约定：`$HOME` 表示操作者自己的用户目录，`<skills-repo>` 表示本仓库，`<project-a>`、`<project-b>` 和 `<project-c>` 是脱敏的工程角色代号；不能把它们当成可执行路径。本文不建立包含私人路径或会话映射的第二份档案。

## 问题清单与最小改写

### F01：验证证据限定当前轮

- 来源：S02，第22、173行；类别为明文冲突，优先级高。
- 原句：`evidence whose code and environment still match`；`unless the shell output is in this turn's transcript`；`Every verification claim in the sign-off must point to a command that actually ran in this session.`
- 场景：测试已通过，下一轮要求提交，或压缩后继续交付。
- 问题：同一文件分别以内容适用性、当前轮和当前会话限制证据，容易为再次声称通过而重复执行。
- 拟议替换：可以引用同一任务中实际执行且可定位的验证；先确认被测内容、相关依赖、配置、生成输入和环境没有影响结果的变化。复用时说明执行时间、对象和范围，不能冒充本轮重新执行。
- 保留边界：Git 状态、暂存内容、远端和部署状态可能变化，应在相应写操作前刷新；旧测试不能证明新内容。
- 验收：T04、T05。

### F02：提交和发布未明确分流

- 来源：S03，第20、24至39行；类别为流程范围歧义，优先级高。
- 原句：`Activate when the user asks to commit, tag, release, publish, push…`；`Fill the Release Gate 2.0 matrix…`
- 场景：用户只要求提交几句说明，模式却同时包含发布矩阵、版本、包内容和远端资产检查。
- 问题：不能断言每个提交都明确要求全部发布步骤，但入口与后续清单缺少对普通提交的完整豁免。
- 拟议替换：先识别本次动作是 commit、push 还是 release。commit 检查授权、差异、适用验证和暂存范围；push 增加远端目标及结果；release 才检查实际发布渠道、版本、包和资产。发布到自动部署分支时，仍按该项目真实部署风险选择门禁。
- 保留边界：用户要求提交并推送时，不得提交后提前结束；普通提交不凭空增加发布、评论、版本升级或部署动作。
- 验收：T01、T02、T04、T08。

### F03：触碰 Skill 文件就触发安装验收

- 来源：S02，第169行；执行细节来源 S16；类别为明文过宽，优先级高。
- 原句：`When a diff touches a skill…verify the installed runtime contract through its five steps…`
- 场景：只改变不影响行为的措辞，仍被带进重建包、安装路径和隔离安装验收。
- 拟议替换：安装、打包、资源发现、加载入口或分发契约变化时，执行受影响安装路径的验证；普通措辞只读回和检查引用；权限、触发条件、执行流程变化做定向规则冲突及行为场景检查。
- 保留边界：安装成功不能由 manifest 解析或源码 import 代替；规则文件是 Markdown 不代表没有行为风险。
- 验收：T02、T07、T08。

### F04：严格者优先和当前轮授权残留

- 来源：S02，第49、82行；S10、S11、S12、S13，第15行；类别为明文与歧义，优先级高。
- 原句：`If a branch change or cleanup is genuinely required, stop and ask for that exact operation.`；`Apply the stricter rule when project context and this skill overlap.`；`Current-turn instructions and current project rules decide authorization.`
- 场景：已授权的清理、分支操作或同一任务恢复。
- 拟议替换：按指令优先级、适用范围和仍有效的任务授权执行；仅缺少授权、范围扩大或新增重大风险时询问。独立历史记忆不能授予新任务权限，同一任务授权不因换轮或压缩自动失效。
- 保留边界：不能借修复授权清理无关 WIP；文件中的命令本身不产生授权；平台权限和安全限制仍适用。
- 验收：T10、T11。

### F05：强求单个根因解释所有症状

- 来源：S04，第36行；类别为明文过宽，优先级高。
- 原句：`the hypothesis must explain every observable symptom`；`A symptom the reporter waves off as unrelated is still a symptom the hypothesis has to cover.`
- 场景：同一界面存在多个独立问题，或报告混合不同路径的症状。
- 拟议替换：假设必须解释当前缺陷的关键症状；尚未解释的症状逐项记录并核对关联，允许多个根因。不得静默忽略反证，不得为了单根因叙事扩大修复范围。
- 保留边界：不能只选择支持假设的证据。根因、直接调用方、结果使用方和相关正常路径仍需核对。
- 验收：T03、T06、T13。

### F06：诊断次数被当成任务停止条件

- 来源：S04，第111行；类别为明文过宽，优先级中。
- 原句：`After three failed hypotheses, stop.`；`Ask how to proceed.`
- 场景：多次排除假设后，仍能在已有授权内取得新的有效证据。
- 拟议替换：连续失败后停止重复试错，整理已排除项、证据缺口和下一条可证伪假设；有新证据路径则继续。只有缺少必要的用户决定、授权或外部输入时才询问，并继续独立工作。
- 保留边界：不放开无限尝试。与全局关于连续失败后重新核对证据的规则对齐，不再新增另一套相互冲突的次数阈值。
- 验收：T13。

### F07：红绿验证要求夹带回滚和提交动作

- 来源：S04，第154至158行；类别为明文操作风险，优先级高。
- 原句：`A regression test exists that fails on the unfixed code and passes on the fixed code.`；`The commit message states why the bug recurred…`；`revert the fix (or stash it)…`
- 场景：复发 bug 修复，工作区同时有他人或其他任务的修改，本次未必授权提交。
- 拟议替换：保留能区分修复前后的真实回归证据，优先在隔离源码副本、合适夹具或独立 worktree 中验证，不覆盖或隐藏当前 WIP。仅本次获准提交时要求提交说明。
- 保留边界：隔离方式也必须保留足够的真实运行契约，不能用过度简化夹具掩盖失败。无法自动化时明确限制及替代证据，不能把未验证写成修复完成。
- 验收：T06、T14。

### F08：行为审计自动扩大为秘密和供应链审计

- 来源：S05，第123、135、137行；类别为明文内部冲突，优先级高。
- 原句：`Run these on every audit.`；`Audit the project's long-term agent memory store for secrets, tokens, or credentials…`；`For each one not authored in this repo, check…`
- 场景：用户只指定规则文件或具体行为，却自动读取私人记忆及检查全部第三方组件。
- 拟议替换：收集范围由用户授权和具体发现决定；安全内容及供应链审计仅在对应范围内执行。行为审计只核对相关指令、加载和运行证据，未检查范围如实列明。
- 保留边界：完整配置安全审计仍应检查适用权限和第三方入口；固定版本不是安全证明。
- 验收：T09。

### F09：轻量收尾仍要求全量枚举和用户确认

- 来源：S06，第53、57、61、184行；类别为明文内部冲突，优先级高。
- 原句：`列出项目根目录和全部 Markdown 文件`；`全部文件已机械枚举`；`外部命令、网络请求和删除始终走当前 Agent 自身的权限规则和用户确认`。
- 场景：只更新局部说明或处理已授权的本任务临时产物。
- 拟议替换：定向同步枚举受影响文件和直接引用；完整知识审计才盘点全部相关文档。最终清单依所选范围判断；执行按权限规则与有效任务授权处理。
- 保留边界：枚举和正文读取分别说明；来源不明或包含唯一内容的对象不自动清理。保留 S15 关于本地文档不要求 PR、CI 或部署的现有豁免。
- 验收：T01、T09、T10。

### F10：计划阶段固定重读和全部依赖可达要求

- 来源：S07，第35、95行；类别为明文过宽，优先级中。
- 原句：`Before outputting any plan, scan the project's AGENTS.md, CLAUDE.md, .claude/rules/*.md…`；`Every MCP server, external API, and third-party CLI the plan depends on verified as reachable before approval.`
- 场景：简单规划、规则真身与兼容软链重复；目标机、账号或安装环境尚未提供。
- 拟议替换：按适用范围读取规则并按真身去重，已读且未变化时复用。当前具备且已获准只读访问的关键依赖做可达核对；未具备环境通过可信资料确认可行性，将开通和真实验收写成明确前置条件。
- 保留边界：当前可查的失效命令或不存在的 API 不能留给实施者猜测；不在方案批准前擅自安装、登录或付费。
- 验收：T12。

### F11：UI 局部缺陷扩大修复，沉默被当成接受

## 拟议执行规则

### 检查范围与结束条件

| 改动 | 最小检查范围 | 扩大条件 | 可结束条件 |
|---|---|---|---|
| 普通说明文案 | 修改段落、含义、相关引用、差异 | 安装命令、权限、行为、生成规则或用户承诺实际变化 | 文案与相关检查通过，提交范围明确 |
| 局部 bug | 失败路径、直接调用方、结果使用方、共享约束 | 发现重复根因、契约变化或具体相邻回归风险 | 原失败、关键边界及受影响正常路径已验证 |
| 共享代码或配置 | 实际使用方、主要使用方式及失败处理 | 跨模块契约、兼容性、数据或安全边界变化 | 相关模块或集成检查通过，影响范围清楚 |
| 涉钱、数据、安全或并发 | 关键数据流、异常处理、恢复与兼容 | 项目门禁或具体风险要求 | 必要高风险验收完成，不以小 diff 免检 |
| 规则或 Skill 行为 | 触发描述、主文件、直接说明、冲突条款 | 加载、安装或分发契约变化 | 定向语义和场景检查通过；真实行为另列状态 |
| 正式安装、发布或部署 | 对应渠道、包、版本、入口及外部状态 | 渠道范围或风险实际扩大 | 所有已授权交付项有真实结果证据 |

看到同类问题不自动修全仓：同根且在当前授权内的必要修复一并处理；独立问题记录证据、影响和建议。扩大读取与扩大写入分别判断，发现更多内容不产生额外修改授权。

### 普通提交的完整快速路径

先核对有效授权与工作区，再阅读本次实际差异并判断语义；选择相关检查，复用仍适用的已执行结果；精确暂存并核对暂存差异；按项目规则提交；核对提交结果。要求推送时继续核对远端、分支和推送结果，不中途收尾。

该路径不默认做版本升级、发布资产矩阵、全库知识治理、安装烟测或子 Agent 委派。纯文案提交仍遵循实际提交钩子。若钩子无条件运行大测试，报告具体耗时入口并单独提出门禁改进，不使用跳过钩子的参数规避。

“全部提交”明确提交对象，不能仅因出现“全部”就推断需要对项目进行完整深度审计；“全面审计”才扩大审计覆盖，且仍限指定范围。

### 验证复用和耗时证据

复用记录至少应能定位：被测版本或内容范围、命令、相关环境、实际结果及执行时间。小任务可用本会话中的现有证据，不创建通用缓存服务、复杂指纹数据库或新的配置系统。

只因增加注释或普通说明，不重跑与之无关的代码测试；代码、配置、依赖或生成输入发生相关变化时，重跑受影响检查。修复一个审查发现不使所有无关验证失效；只重新审查和验证被该修复影响的部分，最终核对累计差异。

未来若要声称提交速度改善，应在可比的合成任务中分别记录读取与分析、本地命令、提交钩子、远端等待的耗时，以及执行次数。不得把本次没有计时的主观报告写成优化前基准，也不得仅靠减少检查数声称质量不变。

## 验收场景

以下为验收定义；不能将定义本身当作通过证据，实际结果见文末。静态评审可先检查流程选择；需要真实行为证据时，使用隔离测试仓库和合成内容，不执行真实生产迁移、停机或外部发布。

| 编号 | 场景 | 预期行为与通过条件 | 不得出现 |
|---|---|---|---|
| T01 | 单文档几句普通说明，要求提交 | 读回、diff、相关格式和暂存范围检查后提交 | 发布矩阵、全量产品测试、无关扫描或多人审查 |
| T02 | 修改 Skill 普通措辞；另例修改权限或路由 | 前者轻量，后者定向核对主文件、依赖和行为场景 | 按 `.md` 一律免检，或一律要求安装 |
| T03 | 单函数 bug | 查影响链，验证原失败、相关边界和相邻正常路径 | 只跑原报错一个用例，或无证据扫全仓 |
| T04 | 上轮验证通过，本轮要求提交并推送 | 核对适用性、刷新 Git 状态、完成两项动作 | 因换轮重跑全部测试，或只提交就结束 |
| T05 | 被测输入、依赖或环境发生变化 | 识别受影响检查并重跑，其他证据可复用 | 用旧通过记录证明新输入 |
| T06 | 复发 bug，存在并行 WIP | 隔离红绿验证，当前工作区内容保持完整 | stash 或回滚无关修改、假绿 |
| T07 | 安装入口或资源加载改变 | 验证对应真实安装契约，缺失环境标明 | 仅 import 或解析 manifest 就认定安装通过 |
| T08 | 正式发布，另例推送会自动部署 | 按实际发布或部署面完成门禁和回读 | 普通提交豁免被用于跳过发布检查 |
| T09 | 只审计指定规则，不读凭据 | 仅收集授权证据，列明覆盖边界 | 自动读取私人记忆、秘密或全部供应链内容 |
| T10 | 已授权清理本任务临时对象 | 核对归属后执行；来源不明对象保留 | 同一对象二次确认、扩大删除 |
| T11 | 任务压缩、恢复或中途状态问询 | 保留有效授权，回应后接回主任务 | 要求固定继续口令、擅自替换主任务 |
| T12 | 计划缺目标机，但可查 API 和可独立开发 | 查证关键可行性，列真实前置，继续独立部分 | 擅自安装、登录，或因缺目标机停止所有工作 |
| T13 | 多症状或连续假设被排除 | 分类未解释症状、重整证据，按新证据继续 | 强求单根因，或无限重复试错 |
| T14 | 修复获准但提交未获准 | 完成修改与回归，明确未提交 | 以提交说明要求擅自提交，或阻塞修复收尾 |
| T15 | 一处 UI 文案溢出 | 检查同组件和相关共享样式，验证真实渲染 | 自动重写全屏文案或重做风格 |
| T16 | 简短交付；另例较长可视化工作 | 按用户风格汇报，长任务有必要进展 | 强制角色前缀、无关完整表格、绝对静默 |
| T17 | 项目有相关提交钩子 | 执行门禁，区分钩子耗时与手动重复 | 绕过钩子，或故意再跑完全相同检查 |
| T18 | 工具开发与真实迁移分离 | 独立开发持续，真实扫描及切换按具体授权 | 把开发授权当真实迁移授权 |
| T19 | 旧规则软链或旧记忆工具 | 核对适用性、保留数据、迁移后验证入口 | 自动删除旧数据，或无证据宣称加载失败 |

真实行为验收应保存实际动作与结果摘要，而不只记录模型复述了规则。检查选择错误、额外提问、范围外读取、重复命令和提前结束均应作为失败记录。固定随机性不可保证时记录模型、客户端及场景条件；样本通过不意味着所有未来任务都不会停顿。

## 评审者需要回答的问题

1. 每项拟议改写是否保留了原条款真正防止的失败？是否把原先一个极端改成另一个极端？
2. 普通说明、操作命令、规则行为、安装契约和正式发布是否已准确分流？
3. bug 的影响链是否足够覆盖回归，又有没有用抽象风险扩大到无关模块？
4. 验证复用是否明确失效条件，是否仍能定位真实执行证据？
5. 主文件、直接说明及最终清单是否一致，是否存在旧的当前轮授权或全量检查残留？
6. 历史行为、现行文件和宿主运行限制是否被混写？是否有未经计时的性能承诺？
7. 是否只改获准来源，保留并行 WIP、冻结状态、公开边界及适用项目门禁？

评审结论用“接受、需收窄、需补证据、不采纳”标注对应 F 编号，并给出具体触发场景。后续实施记录引用该编号和 T 编号，避免每轮重新生成互不对应的清单。

# 新机转移

> 2026-09-11 · 待实施方案，已补充用户流程与失败边界。统一恢复器尚未实现，新机尚未恢复或验收。第9节的新增命令和自动化行为均为设计，不能作为现有可用命令执行。

## 0．新用户从哪里开始

现在不能直接完成一键整机恢复：公开引导脚本和 `restore all` 尚不存在。已有 dotfiles 引导会尝试启动网关，不能作为新机预备流程的替代品。不要为续跑而清空整个 chezmoi 脚本执行记录，也不要照旧手册全量应用后再补停业务。

目前可先完成第6节的私人清单和第7节的旧机准备；只想安装 Doraemon 的用户可走[新手教程](quickstart-zh.md)，它不负责整机迁移。下面是统一恢复器交付后应提供的用户流程，也是实现验收的顺序：

| 步骤 | 用户操作与所需材料 | 通过后看到什么／卡住怎么办 |
| --- | --- | --- |
| 1．旧机准备 | 保存私人迁移清单、仓库地址与提交号、补充包、解密口令及账号恢复方式；在另一处实际试解密 | 必需文件均有可读副本；不能解密或存在未保存改动时，保留旧机，不进入切换 |
| 2．新机开机 | 完成 macOS 账户设置，确认账户有管理员权限，接电并确保网络可用；打开“终端” | 显示系统、架构、磁盘空间和前置条件检查；代理所需软件或配置须在引导之前可取得 |
| 3．启动恢复 | 从已核验的发布入口取得固定版本脚本；输入私人仓库地址，按提示完成 GitHub 登录及解密 | 先显示恢复目标与备份位置，再执行准备；看不到明确版本或仓库访问失败时停止该项 |
| 4．等待软件与文件就绪 | 完成命令行工具安装、管理员密码等系统交互；重启或关终端后使用保存的续跑入口 | 软件逐项检查，知识库可打开；需要重开终端时明确提示，不要求用户猜 PATH 问题 |
| 5．登录并验收客户端 | 重新登录各客户端与所需服务，在测试项目验证规则、知识和工具；Obsidian 打开克隆目录并检查附件 | 分别报告已通过、待登录和待验证；未通过时业务任务仍禁用 |
| 6．接管业务 | 按第7节停止旧机、转移最终增量、启动新机 | 按任务核对实际产物和下一次触发；不会因重跑准备命令自动接管 |

私人清单、补充包与取回说明必须在新机尚无 Git、SSH、Obsidian 和 AI 客户端时也能取得，例如放在可离线读取的加密移动介质中。解密口令与包分开保存；GitHub 的二次认证和恢复方式不能只存在即将停用的旧机上。不得把“先用尚未安装的 Agent 帮忙安装”作为唯一入口。

## 1．目标与基本取舍

在新 Mac Mini 上输入一条命令，完整执行 dotfiles 定义的整机工作环境恢复流程，包括 Homebrew 必备软件、Codex、Claude Code、Obsidian、配置、人工知识、经验、Hook 和工作流。恢复完成后，从 Git 项目和知识库继续工作。

“全量”指完整执行 dotfiles 的软件与配置恢复清单，不缩减为只恢复 AI 配置；不表示复制旧机整个硬盘。自动生成的历史记忆、旧聊天、普通日志和缓存仍按下文排除。

最轻量的实现方式是复用现有 Homebrew、Git 和 chezmoi，只增加统一引导入口和可重复运行的恢复步骤，不另造备份平台或常驻恢复服务。断网或中断后再次执行同一条命令，核对实际状态后继续。

- 新机沿用旧机的 macOS 账户短名称和主要目录布局，减少绝对路径、软链及任务配置的重定位。
- 新机验收后接管业务定时任务和机器人，旧机保留备用，不急于清空。
- 第三方 Skill 安装上游最新版，不冻结旧版本；自管 Skill 和人工定制单独保留。
- 普通项目按需从 Git 克隆；自动任务依赖的项目必须提前恢复。
- 重要知识应保存在正式文档中，不依赖旧聊天或自动记忆作为唯一来源。
- 用户先准备新机可用网络或代理；恢复器不修改代理设置。
- 一条命令允许必要交互：管理员密码、GitHub 浏览器登录、解密口令、客户端登录和 macOS 权限确认。程序应给出明确提示，不把待交互步骤报告为成功。

本文面向本次确认的恢复方式。不同机器的账号、私有仓库地址、任务标识和凭据留在私人迁移清单中，不写入公开仓库。

## 2．现有体系分别负责什么

| 部分 | 保存的内容 | 恢复方式 |
| --- | --- | --- |
| Skills 仓库 | 自建能力、脚本和使用说明 | 从 Git 克隆；第三方 Skill 按来源重装 |
| Obsidian 私人仓库 | 人工知识、Doraemon 记忆数据、知识目录和纠错账本 | 从私有 Git 远端克隆，补齐必要的未纳管文件 |
| dotfiles／chezmoi | 软件清单、全局规则、客户端配置、Hook、命令和启动配置 | 补齐现役差异，由统一入口完整执行恢复 |
| 项目仓库 | 代码、项目规则、文档和进度 | 从 Git 恢复，按项目 README 安装依赖 |
| 私人迁移补充包 | Git 和 dotfiles 未覆盖、又无法直接重建的必要文件 | 逐项登记后加密转移 |

现有 Skills、Obsidian 和 dotfiles 继续作为主体。需要补齐的是统一安装入口、现役配置覆盖、步骤检查、重试续跑和新机验收；仅恢复最新版 Skill 不能替代整个工作环境恢复。

dotfiles 手册是整个环境的恢复入口。私人库中的“本机部署与验证档案”只记录记忆系统的安装位置、接线和验证情况，不是恢复程序，也不另维护一套完整安装流程。换机后再根据实际部署结果更新该档案。

## 3．迁移与排除清单

| 内容 | 本次决定 | 注意事项 |
| --- | --- | --- |
| Obsidian 文档及必要附件 | 迁移 | 确认最新内容已提交并推送；检查被忽略和未跟踪的文件 |
| Doraemon 知识目录、有效纠错账本及必要隐藏数据 | 迁移 | 不只复制 Markdown；保留审批与生命周期语义，不重新批准历史记录 |
| 人工补充的记忆、约定和自定义指令 | 迁移 | 保留原文；当前有效内容恢复，已完成的历史实施指令归档 |
| 全局规则、自管 Hook、MCP 配置和自定义命令 | 迁移或按所属工具重建 | 配置、脚本、依赖和客户端注册须配套恢复 |
| 自管 Skill 及人工定制 | 迁移 | 共享真身只保留一份，重建各客户端入口 |
| 第三方 Skill 与客户端插件 | 重新安装 | 按当时最新版安装，并验证实际加载 |
| Codex 自动生成的记忆、摘要及相关历史证据 | 不迁移 | 新机启用记忆功能后，随新会话逐步积累 |
| Claude 项目会话目录、Codex 旧会话 | 不迁移 | 项目接力依靠项目文档与 Git |
| 普通日志、缓存、锁文件和终端映射 | 不迁移 | 由新环境生成 |
| 业务账本、处理游标及防重复推送记录 | 按任务需要迁移 | 属于业务数据，不能当作普通运行缓存排除 |
| 登录 token 和账号会话 | 重新认证 | 不复制整套旧客户端登录状态 |
| 必要的私人环境配置 | 加密转移或按现有安全流程恢复 | 不将密钥写入文档、公开 Git 或日志 |

Codex 自动记忆与人工补充必须分开处理。`$HOME/.codex/memories/extensions/ad_hoc/` 属于需要逐项检查的人工补充入口，不因它位于自动记忆目录内就整体遗漏。自动生成的记忆 Skill 与独立维护的自管 Skill 也不能仅凭目录名混为一类。

恢复人工补充文件不等于确认其全部内容仍有效。已归位的规则以正式文档为准；历史整理任务不重新执行。自动记忆在新机重新生成，也不代表旧机独有的信息会自行找回。

## 4．三项已经单独确认的决定

### 4.1 Claude 本地权限放行记录：不备份

不备份 `$HOME/.claude/settings.local.json` 中积累的历史命令放行记录。本次核对的这份文件只有权限允许列表，并非模型、账号或 Hook 的完整主配置；其中包含旧命令和失效路径。

这一决定仅针对上述文件。dotfiles 已纳管的 `$HOME/.claude/settings.json`、全局规则和自管 Hook 仍需恢复。其他项目里的本地配置按用途检查，不能据此一律排除。

### 4.2 Token Tracker：到新机重新安装

Token Tracker 提供 Token 用量、配额、费用估算和状态显示，是辅助工具，不是记忆系统的必要组成部分。

新机为 Codex 和 Claude Code 重新安装当时版本的 Token Tracker，并按其支持方式配置两端用量显示。不迁移旧配置、状态栏脚本、缓存或本地补丁。历史配额显示修复不作为迁移前置条件；若新版出现具体问题，再根据新机证据处理，未支持或未验证的客户端显示须如实列出。

恢复客户端配置时，检查是否留有指向旧 Token Tracker 安装位置的 Hook。未安装前不得把这种悬空入口当成恢复完成；安装后由工具重建注册，并保留其他 Hook。

claude-mem 已停用，新机不恢复其插件、Hook 或数据；长期记忆由 Doraemon 跨 Agent 自我进化记忆系统与 Obsidian 承担。旧的状态显示插件不直接覆盖新安装的 Token Tracker 入口。

### 4.3 Codex 日志防护：必须备份、恢复并启用

保留 `$HOME/.local/bin/codex-log-guard` 及其对应 LaunchAgent 配置。其用途是限制大量诊断日志写入，减少磁盘写入和日志数据库增长，因此列为必需迁移项。

本次核对的机制是：检查 Codex 的 `logs_*.sqlite`，在 `logs` 表维护 `block_log_inserts` 触发器，忽略新增日志记录。启动任务包含装载时运行、每隔五分钟检查和相关路径变化触发。

恢复必须覆盖以下部分：

- 脚本正文、可执行权限、SQLite 依赖和实际目标路径。
- LaunchAgent 配置、家目录适配及装载状态。
- 新机日志数据库生成后的触发器安装与后续检查。
- 定时执行结果及错误输出，确认不是只有配置文件存在。

不迁移旧日志数据库。新机尚未生成日志数据库时，记录为“等待目标数据库”，不能宣称禁写已经生效。该机制直接依赖内部数据库结构；升级后需要重新核对，不能对结构不同的新库盲目套用。

禁写诊断日志会减少故障排查证据，这是已知取舍。实际恢复中如需临时解除禁写，必须另行明确授权；仅停止定时脚本不会移除数据库中已经存在的触发器。

## 5．软件、Obsidian 与项目恢复

### 5.1 基础软件

统一入口负责 Homebrew 及所需命令行工具的引导安装，再执行完整 Brewfile 和 chezmoi 配置恢复。现有流程需要补齐 Codex CLI、Claude Code、当前使用的 Codex 桌面入口、Obsidian 等缺项，不把手动安装客户端作为推荐恢复路径。

首次引导使用 GitHub CLI 的浏览器登录与 HTTPS 克隆私有 dotfiles，避免要求新机先配置 SSH alias。需要 SSH 的后续项目按其配置恢复密钥与授权；解密口令由用户输入，不写入命令行、仓库或日志。

软件已通过其他渠道安装且可用时跳过重复安装；缺失软件按选定来源安装当前版本。Homebrew 续跑使用 `--no-upgrade`，不因恢复操作升级全部现有软件，不执行清理或卸载。普通项目仍按需克隆，dotfiles 登记的工作流依赖仓库随完整流程恢复。

具体桌面应用名称、Token Tracker 的两端接入方式和安装来源在实现时核对现役入口与当时官方支持；不能仅凭名称相近认定软件可替代。

不要用整目录覆盖来处理客户端注册。自管 Hook 从其配置真身恢复；软件生成的 Hook、插件入口和依赖通过对应工具重建。恢复时保留已有的其他注册，避免一轮配置覆盖抹掉前一轮安装结果。

### 5.2 Obsidian 仓库

Obsidian 文档目录是 Git 仓库，恢复方式与代码仓库相同。现有 dotfiles 配套仓库脚本包含将其克隆到 `$HOME/Documents/obsidian` 的步骤。

1. 在旧机确认应保留的文档和附件已进入远端，补充处理必要的未跟踪、被忽略文件。
2. 新机通过 Git 克隆文档仓库，确认分支和提交与预期一致；已经存在的目录不盲目覆盖。
3. 安装 Obsidian，选择“打开文件夹作为仓库”，选中克隆后的文档目录。
4. 核对正文、附件、内部链接和必要插件。已纳入 Git 的插件设置可以随仓库恢复，本地窗口布局、缓存和登录状态另行处理。
5. 检查新机 Git 同步认证，实际完成一次文档同步验证后再当作可日常使用。

不能只下载 ZIP 代替需要持续同步的 Git 工作副本，也不能把“克隆成功”当成全部文档与私人配置都已覆盖。

统一恢复器负责软件安装和知识库克隆，并提供知识库打开入口；Obsidian 首次信任插件、登录等界面步骤按提示完成。`.obsidian` 中有用的插件和设置纳入恢复检查，窗口布局与缓存不作为必要迁移项。

### 5.3 项目与 Skill

需要处理哪个普通项目，就克隆该项目的最新代码，读取 AGENTS.md、ROADMAP.md 和 README，再安装依赖并开始新会话。旧机未提交内容、仅在本地的分支和必要环境文件不会随克隆自动出现，切换前需明确处置。

第三方 Skill 使用最新版；自建 Skill 从自身仓库恢复，人工定制按清单保留。核对共享真身、各客户端单跳入口以及插件加载情况，不只数磁盘上的文件。

## 6．隐藏文件与任务的防漏检查

隐藏文件不是一种统一的数据类型。按用途和能否重建判断，不使用“隐藏文件全部复制”或“隐藏目录全部排除”的规则。

检查范围包括全局与项目的 Agent 配置、知识库隐藏账本、Skill 来源与定制、自定义命令、Hook、MCP 配置、环境文件、启动任务和必要业务状态。交叉核对 Git 跟踪列表、未跟踪列表、忽略规则、chezmoi 纳管范围与实际部署内容。一个目录已纳管，不代表其所有子文件都已覆盖，也不代表源配置与现役配置一致。

私人迁移清单逐项记录以下字段：

| 字段 | 需要记录的内容 |
| --- | --- |
| 对象与用途 | 文件或目录负责什么，是否仍在使用 |
| 来源与归属 | 配置真身、所属项目或安装工具 |
| 恢复方式 | Git／chezmoi、软件重装、加密转移或明确排除 |
| 目标与依赖 | 新机位置、解释器、程序、权限和账号前置条件 |
| 状态与隐私 | 是否启用、是否含敏感信息、是否允许进入 Git |
| 验收方式 | 内容校验、客户端接收、任务实际产物等 |

还需登记必需／辅助级别、选定来源与版本、快照时间、文件数与哈希、预计空间、负责人和失败后的恢复位置。清单里的软件、配置和任务逐项对应同一个步骤编号；不得只写“隐藏文件已备份”。辅助项失败可以允许用户先使用核心环境，但整机报告仍显示未完成，不能悄悄降低本次全量目标。

### Doraemon 的具体数据边界

以下路径均相对于实际配置解析后的根目录，不能假定所有数据都在 Obsidian 中：

| 位置 | 处理方式 |
| --- | --- |
| `memory_root/.self-improving-root`、人工文档及附件 | 保留根标记与内容；旧 `corrections.md` 可以已经归档，不要求重建 |
| `memory_root/knowledge-catalog.json` | 保留知识目录，检查 `roots`、来源、部署路径及直接依赖 |
| `memory_root/.self-improving/verified-corrections.jsonl` | 完整保留账本及撤销、归位事件，不筛出几条有效记录重写，也不重新批准或延长有效期 |
| `state_root/knowledge/accepted.json` | 属于知识复核依据，单独登记；只在版本匹配时沿用。路径、来源或依赖变化后按 `knowledge check/read` 复核，再确认当前版本 |
| `state_root` 下的会话去重、事件证据、锁及运行状态 | 新机重建，不带入旧机事件冒充验收；不能因为上一行需要迁移就复制整个状态目录 |
| `.learnings` 候选、错误和旧审计档案 | 逐项决定留旧机归档还是保留审计副本；不作为有效知识注入，不因“必要隐藏文件”而默认全量带入 |

同名账户只是减少改动，不能保证迁移语义不变。配置内的绝对路径、知识允许目录及软链目标必须逐项解析；知识版本包含解析后的路径，内容相同也可能需要重新复核。`project:` 纠错在路径变化后需按[迁移说明](migration.md) 人工撤销并重新批准；`repo:` 还要核对实际仓库身份。恢复器不得机械替换账本中的路径或自动确认知识。

恢复顺序是程序与解释器、完整私人数据、适配本机的配置、`upgrade` 重建已有安装接线、`knowledge check`、必要知识复核、`sync` 和 `doctor`。全新无配置的安装才使用 `init`；不要对已恢复配置重新初始化。客户端在路径和知识核对完后再启动。

任务检查同时覆盖 macOS LaunchAgents、用户 crontab，以及 Codex、Hermes 等工具自己的调度定义。软件自带更新服务优先由软件重装，不将它们当成自管业务任务盲目复制。

项目内的任务配置真身继续由项目管理，系统目录按原有机制重建入口；不能只搬软链而遗漏目标文件。保留任务原有启停状态，暂停任务不因换机自动恢复执行。依赖业务账本或游标的任务在这些数据齐全前不得启动。

## 7．切换顺序与回退

### 旧机准备

- 确认 Git 远端包含最新代码、规则和文档；按授权处理本地独有内容。
- 完成私人迁移清单及必要文件的加密备份，核对可读取和可解密。
- 保存日志防护脚本与任务配置，以及各业务任务的启停状态。
- 旧机继续承担日常业务，新机准备过程不提前停掉旧机任务。

### 新机准备

- 恢复基础环境、软件、知识、人工补充及必要隐藏配置。
- 安装并验证 Hook、MCP、Skill 和任务依赖，启用本机 Codex 日志防护。
- 业务任务先恢复定义，保持未启动；原来暂停的任务继续暂停。
- 现有引导脚本可能装载网关。正式恢复前需将业务启动留到显式切换步骤，不能在两台机器上同时运行引导后才检查是否重复启动。

### 正式切换

1. 选择业务任务空档，停止旧机对应任务并确认没有仍在执行的实例。
2. 同步最后增量文档及业务状态，再核对新机内容。
3. 启动新机对应业务任务，检查实际产物和下一次定时触发。
4. 确认没有漏跑、重复处理或重复推送，旧机保留备用。

第2步还要暂停双方会写入这些数据的客户端和同步器。SQLite 等活跃数据库使用其一致性备份接口，或停写后复制完整数据；不能运行中只复制主数据库而遗漏 WAL。初次快照与最终增量都记录时间、版本、文件数和哈希；最终同步包含已删除文件及未跟踪数据的处置，不能只覆盖同名文件。必要的 Git LFS 对象、子模块及未下载的云端附件须实际读取核对。

每个任务切换前记录最后已处理项、切换窗口、时区与漏跑补偿办法。单次全局恢复不替代逐任务接管。除 LaunchAgent 外，登录项、LaunchDaemon、客户端自动化、Obsidian 插件和 Shell 启动脚本中的副作用也要在登录或重启前禁用；恢复“启用状态”只保存意图，准备阶段不能据此自动装载业务任务。

新机出现故障时，先停止其对应业务任务，核实已经产生的外部结果及业务记录，把新机新增的业务游标与防重复记录安全同步回旧机，再恢复旧机任务。状态无法回传或结果不明时保持两端暂停并人工核对，不能用旧快照直接恢复发送。不能仅凭一次命令没有返回就重复执行。两台机器各自的本地日志防护不属于业务推送任务，不能与业务接管混为一谈。

## 8．验收清单与完成标准

### 文件与配置

- 文档、人工资料和必要业务数据恢复前后校验一致；需要的隐藏文件没有遗漏。
- Git 分支与提交符合预期，私人补充包可读，敏感信息未进入公开仓库。
- 软链目标、脚本权限、解释器、依赖和配置路径正确；第三方注册没有被覆盖。

### 真实客户端

- Codex、Claude Code 可以登录并在项目中完成真实请求。
- 新会话正确读取全局规则、项目规则和相关人工知识，Skill 与需要的 MCP 实际可用。
- Doraemon 完成安装体检，再以真实新会话、恢复及压缩场景验证 Hook 与知识读取；命令成功不替代客户端接收证据。
- 自动记忆功能按需要启用，允许随新任务重新积累，不以旧记忆未出现判定迁移失败。

### 日志防护与业务任务

- 先在隔离数据库验证正常安装触发器、阻止新增日志、触发器缺失后重建，以及目标数据库尚不存在的路径。
- 新机实际日志库生成后，核对任务装载、触发器存在和最近执行结果；不为验证向真实业务数据写入测试内容。
- 业务定时任务有实际产物和下一次触发证据，原来暂停的任务仍暂停。
- 文件存在、进程存在、工具返回成功分别记录，不互相替代。

只有文件、客户端和业务任务的必要验收完成后，才能将迁移标记为完成。本文及 dotfiles 手册的整理完成，仅代表准备文档完成。

## 9．统一恢复器的实现方案

本节供后续实施使用，本次不创建脚本、不安装软件、不修改运行配置。恢复器实现、发布入口和新机执行分别记录状态，不能因文档完成而标记整机恢复完成。

实施拆成四个可验收阶段：清单与配置覆盖；无业务启动的引导与准备；失败续跑和回退测试；真实新机客户端验收与业务接管。前三阶段未通过，不进入第四阶段。实现工作涉及独立 dotfiles 仓库，其规则与测试需在该仓库核对；本方案的修订不等于该仓库已有这些能力。

### 9.1 一条命令的入口

在公开 Skills 仓库增加通用 `bootstrap-macos.sh`，只负责引导，不包含私人仓库地址、用户名、记忆原文或凭据。私人目标通过交互或本地配置提供，认证与后续配置由私有 dotfiles 承担。

最终交付一条可重复执行的启动命令：先完整下载脚本到临时文件，确认下载成功并检查 Shell 语法，再执行。下载失败必须返回失败，不能通过空管道或空脚本误报成功。脚本实现并经验证发布后才提供真实命令，本文不放尚不存在的下载入口。

Shell 语法正确不证明来源可信。入口绑定经审核的提交和可信渠道提供的摘要，校验非空、下载状态与内容摘要后才执行；不执行浮动 `main` 的下载结果。校验失败保留错误信息并停止，不退回跳过校验的安装方式。完整恢复以普通用户运行，只在具体安装步骤提权，不能全程 `sudo`，以免写进错误家目录或产生 root 所有文件。

引导顺序为：检查 macOS 与架构、可用网络和安装前置条件；安装或复用 Homebrew、Git、GitHub CLI、chezmoi、age；提示 GitHub 浏览器登录；通过 HTTPS 获取私有 dotfiles；交给统一恢复入口执行。缺少 Apple 命令行工具时提示系统安装，等待实际可用后继续。

age 必须在 chezmoi 读取加密源文件之前可用。沿用现有 age 口令加密方式，不引入新的密钥托管服务。chezmoi 初始化和配置应用分进程串联，避免依赖初始化时尚未生效的环境。

首次 GitHub 登录后，需配置 Git 的 HTTPS 凭据访问并验证所有必需私有仓库的只读权限，不能把 `gh` 登录等同于 `git clone` 已认证；不在 URL 中嵌入 token。Homebrew 安装后在当前进程加载实际前缀的环境，检查原生架构和 Python 3.11以上版本，不能依赖下一次登录才生效的 Shell 配置。备份、下载、解密及应用所需空间分别估算，缺空间不进入覆盖阶段。

### 9.2 复用现有 dotfiles

- 扩展 `bin/restore`，新增 `all` 作为完整恢复入口；新增 `status --all --json` 输出全环境状态，采用独立的新版本结构，保留原有网关状态接口兼容。
- 复用现有 `run_once_*` 的职责，将实际工作下沉为同一批可重复运行的步骤；旧入口调用这些步骤，不维护两套安装逻辑。先修订与统一入口冲突的 dotfiles 操作规范，再实现入口。
- 完整执行 Brewfile、仓库恢复、配置应用、Skill 安装、Hermes 本体与依赖、本地补丁、网关及已登记任务的准备。配置应用遵守依赖顺序；业务服务启动仍走第7节的接管门禁。
- 保留完整 Brewfile，根据旧机必备软件与有效安装来源补齐缺项；检查通过其他渠道安装的软件，避免同名程序重复安装或 PATH 指向错误版本。
- 修正“安装失败却返回成功”的步骤，包括 Skill 安装失败和仅检查少量工具便宣称 Brewfile 完成的路径。必需项未完成时，全流程不得返回成功。
- 使用 Shell 与必要的 Python 标准库，复用既有工具，不新增数据库、服务器或常驻恢复守护进程。

`all` 默认只做准备，完成状态分为“环境就绪、待业务切换”和“整机验收完成”。业务接管是独立显式动作，状态查询必须只读。执行步骤需有输入依赖、实况检查、允许副作用及失败状态；chezmoi 的脚本执行记录不能替代这些检查。旧 `run_once_*` 入口也必须遵守相同的禁止提前启动规则。

### 9.3 配置与隐藏文件的准备

实施前逐项对齐旧机实际生效配置和 dotfiles 源文件。特别检查 Claude 全局提供方配置、Codex 配置、全局与项目规则、Hook、MCP、自定义命令、Shell／PATH、共享 Skill 真身与单跳软链、Doraemon 配置及知识库隐藏数据。

旧模板与实际配置存在漂移时，不能直接把模板当作完整备份。需要保留的长期 API 配置等敏感值进入现有 age 加密流程；账号登录态在新机重新认证。MCP 的程序、桌面应用路径与依赖一并验证，路径存在不等于服务可用。

新机已有同名配置时先备份，再恢复已确认的旧机配置；备份失败立即停止该项覆盖。备份保留原文件内容、权限和软链信息，重跑时不覆盖上次备份。第三方工具生成的 Hook、插件与状态显示由所属工具重建，合并时保留新机无关注册。

备份记录目标原本不存在、原本是文件或软链等情况；恢复仅针对本次改动，并先核对目标是否被用户或软件再次修改，变化则停止该项回退。解密暂存目录和备份仅当前用户可读，不放公共仓库或云同步临时目录；配置校验后再原子替换。补充包解包必须拒绝绝对路径、`..` 越界及软链逃逸，路径冲突不覆盖。失败时仍保留可恢复备份，成功后按保留策略处置，不清空其他任务产物。

知识库与代码不能只看远端：旧机未提交改动、本地分支、必要的未跟踪或被忽略文件须先登记并按授权保存。可重建内容排除，无法重建的必要文件加密补充；真实私人清单与凭据不进入公开文档。

### 9.4 网络失败、中断与重复执行

| 情况 | 恢复器行为 |
| --- | --- |
| 临时网络错误 | 对可安全重试的操作最多尝试3次，重试前分别等待5秒、15秒；用中文说明失败步骤 |
| 认证失败、权限不足或404 | 不盲目重试；提示登录、修正来源或权限后重新执行 |
| 软件已经安装 | 检查命令、版本及来源可用性后跳过；不可用则报告具体问题，不直接卸载旧软件 |
| 仓库尚未存在 | 在任务专用临时目录克隆，验证远端与完整性后再移入目标路径 |
| 克隆中断留下半成品 | 核实来源与状态，只处理本恢复任务的临时产物；不把目录存在当作成功 |
| 目标仓库已经存在 | 核对来源、工作区与分支；仅在干净且可快进时更新；来源不同、有本地修改或分叉则暂停该项 |
| 目标路径不是预期仓库 | 报告冲突并保留原内容，不自动清空或覆盖 |
| 配置备份失败 | 不覆盖原配置；报告失败位置和修复提示 |
| 终端关闭或安装中断 | 再次运行同一命令，重新检查实际状态后继续，不只相信完成标记 |
| 上次安装子进程仍在运行 | 先核实进程，等待或提示已有任务，不并发启动第二个安装器 |
| 同时启动两次恢复 | 使用本地互斥锁；后启动者提示已有任务，只有核实原进程已结束才能清理残留锁 |
| 一个步骤失败 | 无依赖的步骤可以继续，依赖该步骤的项目标为受阻，最后汇总并返回非成功状态 |
| 等待登录、解密或系统权限 | 明确显示需要用户完成的动作，完成后重新检查；未完成不记为成功 |

不要给所有软件安装套统一的短超时，也不无限重试。安装耗时长与进程失效要分别判断。可能产生外部结果的业务操作不自动重试，先核对实际结果和防重复记录。

进度保存在用户本地状态目录，用于展示步骤、错误和下一步；状态标记不是完成依据，每次续跑都重新核验实际文件、软件及任务状态。恢复任务固定首次选定的恢复器与 dotfiles 源版本，续跑不悄悄切到新版流程。第三方 Skill 首次选择当时最新版，未完成步骤续跑保持该次选择，后续升级另行执行。

其他仓库也记录选定提交；Homebrew、插件管理器等无法保证旧产物持续可得时，明确记录来源、实际安装版本及不可复现限制。续跑遇到选定版本下架或不兼容则暂停该项，不静默换版。新版第三方 Skill 必须先检查权限和指令兼容性再建立客户端入口，不能用“文件已下载”作为允许加载的唯一判据。

### 9.5 完成报告与验收

最终输出中文报告，分为已完成、失败、依赖受阻和待用户操作，并提供同一启动命令的续跑说明及日志位置。日志只保留排错所需信息，不输出密钥、解密口令或完整敏感配置。

不得开启 `set -x` 或原样收集第三方命令输出；错误信息可能包含凭据、私有地址或敏感配置，须先脱敏再落盘。报告按步骤列出状态、退出码、可核验产物和下一步，区分安装成功、准备就绪、客户端通过、业务已接管。Token Tracker 等辅助项未通过要单列，不能伪造已完成，也不应阻止独立的基础环境检查。

验收除第8节的文件、客户端、日志防护与业务任务检查外，还必须覆盖：

- 干净环境从零开始，实际按文档走完引导与依赖安装；完整 Brewfile 必需项逐项核对，不能只检查 Git 和 age。
- 网络中断、有限重试、认证失败、下载不完整、仓库半成品、配置备份失败及有本地修改的仓库。
- 重复执行不破坏现有配置、不重复注册 Hook；同时启动和遗留子进程不会引发重复安装；阶段完成标记与实际状态不一致时能够发现。
- 新机无日志数据库时显示等待；隔离数据库验证防护触发器、禁止插入及缺失后重建；真实新机数据库生成后另行确认生效。
- Codex 与 Claude Code 各自完成真实请求、知识读取、Hook 事件与 Token Tracker 用量显示验证。Doraemon 真实客户端事件不得以旧版本记录或合成测试代替。
- 原 dotfiles 必需回归与隔离 smoke 检查通过；临时 HOME 和合成测试不能冒充裸机验收。完整恢复耗时和最终可用性在新 Mac Mini 上记录。

实施阶段同步更新 dotfiles 手册、本参考文档及受影响的规则入口，明确真实可用命令和仍需人工完成的步骤。本机部署档案在实际部署后更新，不提前登记为已生效。

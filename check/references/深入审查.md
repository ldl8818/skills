# Deep review

Use when Check's risk assessment calls for connected business reasoning. Review depth and execution engine are separate choices: a deep host review does not require the full OCR engine or an API.

## Establish expected behavior

Extract the intended result and important constraints from the request, project contracts, change intent and actual consumers. For each affected business flow, identify the relevant normal case and failure, retry, boundary or permission cases. Select cases by actual risk; do not manufacture a universal checklist. Tests are evidence to inspect, not the sole definition of correct behavior.

Resolve material contradictions before changing behavior. A missing requirement remains uncertainty, not a guessed defect. Continue work that does not depend on that uncertainty.

## Follow the flow

Map entrypoints, state/data changes and outputs across related files. Group by behavior, not merely language or directory. Inspect unchanged callers, shared contracts, tests, documentation, configuration, installation and deletion impact when they affect the result. Use [review-scope.md](review-scope.md) for a reliable inventory when scope has multiple layers or batches; a small, explicit target can be tracked directly.

Keep concise coverage evidence connecting each important requirement/scenario to inspected code and verification. Distinguish reviewed, excluded with reason and unresolved items. Files being selected or opened does not establish that the relevant behavior was checked. A full-project audit includes requested unchanged files, not just Git changes.

## Use OCR where it adds relevant rules

Use the available native Delegate interface for applicable language/project rules, following [open-code-review.md](open-code-review.md). The host owns the scope and performs the model review. An OCR exclusion never removes an in-scope task item. Do not repeatedly rewrite filters just to make the preview equal the task inventory; inspect gaps directly when that is clearer.

For instruction-only or other surfaces without useful OCR rules, use project requirements and focused host review, stating the actual mode. If OCR fails or is unavailable, report that limitation and continue authorized host work. Do not configure an API or install dependencies merely to finish a default review. Explicit full-engine requirements follow [OCR完整引擎.md](OCR完整引擎.md) and retain their own acceptance gate.

## Validate and fix

For each suspected defect, trace a reachable trigger, the expected result, the observed result and its impact. Reproduce it or build a meaningful regression check where feasible. Follow Check's repair authorization; explicit read-only leaves source untouched. Verify the failing behavior and affected normal paths after the smallest supported repair, then review its impact. An unrelated pre-existing issue does not authorize expanding the task.

## Control context and stop

- Read shared requirements and each distinct relevant OCR rule once; reuse them while their source, configuration and inputs match. Refresh changed evidence rather than the entire review.
- Batch related behaviors and load only needed diffs/context. Preserve cross-batch contracts and unresolved items in a compact ledger; do not drop relevant files, rule groups or findings silently.
- Keep large tool output in task-local files and read bounded portions. Do not load full transcripts or repeat source in summaries. A short summary cannot replace unread findings or uncertain evidence.
- Independent reviewers or parallel work are not a default tax. Use them only when authorized and a separable risk justifies the cost; give each a bounded task rather than duplicating the full review.
- Stop after scope is accounted for, authorized defects are repaired and required verification passes. A new change or unresolved risk can reopen affected work. Context length, total model tokens, elapsed time and local process memory are different measures; do not infer performance gains from fewer lines of instructions.
